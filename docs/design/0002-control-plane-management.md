# 0002: Control-plane management

Status: Proposed

Authors: Stephen Cox; drafted by Claude (Claude Code)

## Context

A future central control plane will provision and manage every instance of mitm-proxy. This record
defines the instance's side of that: how it is identified and enrolled, how it receives configuration,
how it reports what it is actually running, and what its local HTTP API becomes. The control plane is a
separate project. This record specifies the protocol it has to implement, and nothing else about it.

It builds on [0001](0001-initial-design.md), which is still Proposed. Where the two conflict, this record
wins. It replaces 0001's admin API endpoints (except `/healthz` and `/readyz`, which stay as they are) and
0001's middleware loading. It also splits 0001's settings into local and managed ones.

Constraints:

- **Where instances run:** lab networks, behind NAT, on restricted VLANs, and in Kubernetes behind
  NetworkPolicies. The control plane often can't reach an instance. An instance can almost always reach
  out over HTTPS.
- **Fail closed:** the admin API stays on `127.0.0.1` (0001), and nothing on it can change state.
- **Static stability:** a control-plane outage must not affect traffic. An instance keeps running its last
  applied configuration indefinitely.
- **The control plane must not be able to run code** on an instance, or obtain its private keys.
- **Standalone mode stays:** with no control plane configured, mitm-proxy works exactly as 0001 describes.
- **Standards:** we copy the concepts of OpAMP (OpenTelemetry's Open Agent Management Protocol) without
  taking its transport or protobuf. Moving to OpAMP later should be a change of transport, not a redesign.

## Decision

### Modes

- **Standalone** (`control_plane.url` empty): every setting is local, as in 0001.
- **Managed** (`control_plane.url` set): settings are split into two groups.
  - **Bootstrap** settings are local only. They say who the instance is, where the control plane is, and
    where to listen.
  - **Managed** settings come only from the control plane.

  Setting a managed key locally (in the YAML file, an env var or a `_FILE` variable) is a `ConfigError`
  at startup, which exits with code 2. Two writers for one setting never happens silently.

| Group | Settings |
|---|---|
| Bootstrap (local) | `log_level`, `listen.*`, `state_dir`, `proxy.host`, `proxy.port`, `proxy.shutdown_grace_ms`, `ca.*` (standalone CA only), `middleware.available`, `control_plane.*`, `instance.labels` |
| Managed | `intercept.hosts`, `middleware.chain`, `middleware.hook_timeout_ms`, `body.max_buffer_bytes`, `proxy.auth`, `proxy.peek_timeout_ms`, `proxy.idle_timeout_ms`, `upstream.extra_ca` (PEM content; locally it is `upstream.extra_ca_file`), `upstream.connect_timeout_ms`, `upstream.idle_timeout_ms`, `upstream.max_connections_per_host` |

### Middleware by name only (changes 0001, both modes)

- `middleware.available` (bootstrap, list of `name=module:attribute`) is the local registry of what is
  installed and allowed to run. The built-in `log` (`FlowLogger`) is always available.
- `middleware.chain` (managed in managed mode, local in standalone) is now an ordered list of **names**
  from that registry.
- A chain naming an unknown middleware is invalid. In standalone that is a `ConfigError`; in managed mode
  the configuration fails to apply (status `FAILED`).

The control plane can choose and order middleware. It can never make an instance import a module.

### Identity

- **Instance UID:** a UUIDv7, generated by the instance on its first start and kept in
  `<state_dir>/instance-id`. This follows OpAMP: the agent owns its ID. Python 3.13 has no `uuid.uuid7`
  (it arrives in 3.14), so a small helper generates it until then. `mitm-proxy instance id` prints it, for
  operators who pre-register instances.
- **Description** (sent to the control plane), using OpenTelemetry semantic-convention keys:
  - identifying: `service.name` (`mitm-proxy`), `service.version`, `service.instance.id` (the UID);
  - non-identifying: `host.name`, `os.type`, and the `instance.labels` setting (`key=value` pairs) for the
    control plane's grouping;
  - `config_schemas`: the managed-configuration schema versions this instance understands, for example
    `["mitm-proxy.config/v1"]`.
- **Capabilities** (strings, so new ones can be added without breaking anything): `reports_status`,
  `reports_health`, `reports_effective_config`, `accepts_remote_config`, `accepts_certificates`. Unknown
  capabilities are ignored on both sides.

### Transport: one exchange endpoint, long-polled

The instance talks to the control plane with a single request, modelled on OpAMP's HTTP transport, plus
a long-poll so that changes arrive without delay:

```text
POST {control_plane.url}/v1/instances/{uid}/exchange?wait_ms=50000
Content-Type: application/json
Body: InstanceReport  →  200 ControlResponse | 4xx/5xx application/problem+json (RFC 9457)
```

- HTTPS only. `http://` URLs are a `ConfigError`.
- The control plane is verified against `control_plane.ca_file` when that is set. The bundle **replaces**
  the system store for this one connection, which pins it to a private CA. Otherwise the system store is
  used.
- **Long-poll.** If the control plane has nothing new for the instance (judged from the instance's
  reported config hash and certificate state), it may hold the response for up to `wait_ms`. Then it
  answers with an empty `ControlResponse`.
- **Reporting early.** When the instance has something new to report (an apply result, a health change, a
  certificate request), it cancels the pending request and sends a new exchange at once. The control plane
  treats the highest `sequence_num` as current.
- **Wait time.** `control_plane.wait_ms` defaults to **50 s**, below the 60 s idle timeout common in load
  balancers and proxies. The control plane can lower it per instance (`poll.wait_ms`).
- **Backoff.** Errors and connection failures back off exponentially with full jitter, from 1 s up to a
  5-minute cap. The instance honours `Retry-After` on `429` and `503`. None of this is configurable.

### Messages

All timestamps are RFC 3339 in UTC. Hashes are `sha256:<hex>` over the canonical JSON of the value. The
canonical form is RFC 8785 (JCS). Our payloads contain no floats and only ASCII keys, so
`json.dumps(sort_keys=True, separators=(",", ":"), ensure_ascii=False)` produces it.

**InstanceReport** (instance → control plane). This is OpAMP's `AgentToServer`. Fields that haven't
changed since the last acknowledged report are left out, unless the control plane asked for full state.

```json
{
  "instance_uid": "01928c7e-6f1a-7b3c-9d2e-4f5a6b7c8d9e",
  "sequence_num": 42,
  "capabilities": ["reports_status", "reports_health", "reports_effective_config",
                   "accepts_remote_config", "accepts_certificates"],
  "description": {
    "identifying": {"service.name": "mitm-proxy", "service.version": "0.3.0",
                    "service.instance.id": "01928c7e-6f1a-7b3c-9d2e-4f5a6b7c8d9e"},
    "non_identifying": {"host.name": "lab-proxy-1", "os.type": "linux",
                        "labels": {"site": "lab-a"}},
    "config_schemas": ["mitm-proxy.config/v1"]
  },
  "health": {
    "healthy": true, "status": "serving", "start_time": "2026-10-28T09:00:00Z", "last_error": null,
    "components": {
      "proxy_listener": {"healthy": true, "status": "listening"},
      "ca": {"healthy": true, "status": "loaded"},
      "control_plane": {"healthy": true, "status": "connected"}
    }
  },
  "remote_config_status": {"last_remote_config_hash": "sha256:…", "status": "APPLIED",
                           "error_message": null},
  "effective_config": {"hash": "sha256:…", "config": {"…": "…", "proxy": {"auth": {"set": true}}}},
  "certificates": {"client": {"not_after": "2026-11-27T09:00:00Z"},
                   "ca": {"not_after": "2026-11-27T09:00:00Z"}},
  "certificate_requests": [{"kind": "ca", "csr": "-----BEGIN CERTIFICATE REQUEST-----…"}]
}
```

- `remote_config_status.status` takes OpAMP's values: `UNSET`, `APPLYING`, `APPLIED`, `FAILED`. A
  `FAILED` status carries `error_message`: one line naming the setting and the reason.
- `effective_config` is the managed configuration the instance is **actually running**, which can differ
  from what it was last sent (after a `FAILED`, it is the previous configuration). Secret values are
  replaced by `{"set": true|false}`. **A hash of a secret is never sent:** a password with low entropy can
  be brute-forced from its hash. The control plane knows whether a secret was applied from the config hash.

**ControlResponse** (control plane → instance). This is OpAMP's `ServerToAgent`.

```json
{
  "instance_uid": "01928c7e-6f1a-7b3c-9d2e-4f5a6b7c8d9e",
  "flags": ["report_full_state"],
  "remote_config": {"hash": "sha256:…", "config": { "schema": "mitm-proxy.config/v1", "…": "…" }},
  "certificates": [{"kind": "ca", "chain": "-----BEGIN CERTIFICATE-----…"}],
  "poll": {"wait_ms": 50000}
}
```

Every field is optional, and an empty object means "nothing new". The control plane sets
`report_full_state` when it has lost state, or sees a gap in `sequence_num`. Unknown flags are ignored.

**Managed configuration** (`remote_config.config`, schema `mitm-proxy.config/v1`):

```json
{
  "schema": "mitm-proxy.config/v1",
  "intercept": {"hosts": ["example.org", "*.example.org"]},
  "middleware": {"chain": ["log"], "hook_timeout_ms": 5000},
  "body": {"max_buffer_bytes": 67108864},
  "proxy": {"auth": "user:password", "peek_timeout_ms": 1000, "idle_timeout_ms": 120000},
  "upstream": {"extra_ca": "-----BEGIN CERTIFICATE-----…", "connect_timeout_ms": 10000,
               "idle_timeout_ms": 60000, "max_connections_per_host": 6}
}
```

- An omitted key takes its default from `SETTINGS`. (It can't take a local value, because managed keys
  can't be set locally.)
- **Unknown keys and unknown `schema` values are rejected** (`FAILED`). The control plane must send only
  the schemas the instance lists in `config_schemas`. That is how schema versions are rolled out across a
  fleet running mixed versions.
- The schema is defined once, as Pydantic models in `src/mitm_proxy/management/protocol.py`. Pydantic
  comes with FastAPI. The models generate the JSON Schema published on the wiki, and the same validators
  as `config.py` run on both paths.

### Enrollment and certificates

The instance generates every private key itself, and no key ever leaves it. The control plane signs
certificate signing requests (CSRs). This follows the same idea as EST (RFC 7030) and OpAMP's CSR flow,
carried inside the exchange.

1. **Enrollment.** The instance has no client certificate in `<state_dir>/identity/`. Its first exchange
   is authenticated with `Authorization: Bearer <control_plane.enrollment_token>` and carries
   `certificate_requests: [{kind: "client", …}, {kind: "ca", …}]`. The control plane answers with the
   signed chains. Every later exchange uses **mTLS** with the client certificate, and the token is never
   sent again. The token is single-use, and enforcing that is the control plane's job. The recommended
   client identity is a SPIFFE ID (`spiffe://<trust-domain>/mitm-proxy/<uid>`). The instance treats the
   certificate as opaque.
2. **Fleet CA.** In managed mode, the instance's CA is an **intermediate** signed by the control plane's
   fleet root, using a `ca` CSR. Leaf certificates are served with the chain leaf → intermediate. Clients
   trust one fleet root instead of one root per instance. The control plane may put X.509 name
   constraints on the intermediate. If it does, the instance rejects (`FAILED`) any configuration whose
   `intercept.hosts` falls outside the permitted names, so that it never mints a certificate clients would
   refuse. Standalone mode keeps 0001's self-generated root.
3. **Renewal.** At two thirds of a certificate's lifetime, the instance sends a new CSR in
   `certificate_requests`, with a new key. It swaps the certificate in when the signed chain arrives.
   Existing connections are unaffected.
4. **Rejection.** On `401` or `403` (a revoked or expired client certificate, or an unknown instance),
   the instance does **not** re-enroll by itself, because the token has already been used. It keeps
   serving its last good configuration, reports the error through `/v1/status`, `/metrics` and an ERROR
   log, and keeps retrying with backoff. To re-enroll, an operator gives it a new token and deletes
   `<state_dir>/identity/`.

### Applying configuration

1. Receive `remote_config`. Report `APPLYING` if validation will take noticeable time.
2. Validate **everything** before changing anything:
   - the schema and every value (the same validators as `config.py`);
   - every middleware name is in `middleware.available`;
   - every PEM parses;
   - the allowlist fits within the intermediate's name constraints.
3. Build a new, immutable runtime snapshot and swap it in with one reference assignment. New connections
   use the new snapshot. Connections already open finish on the one they started with. If upstream
   settings changed, a new upstream pool is created and the old one drains.
4. Write the configuration and its hash to `<state_dir>/managed/last-known-good.json` atomically: write to
   a temporary file, `fsync`, rename, mode `0600` (it contains `proxy.auth`).
5. Report `APPLIED` and the new `effective_config`. If any step before the swap fails, report `FAILED`
   with the reason and keep running the previous snapshot. A configuration is never half-applied.

**Startup in managed mode:**

- If a last-known-good configuration exists, the instance applies it and serves at once, then connects to
  the control plane.
- If none exists (first boot), **the proxy listener isn't bound** until the first configuration has been
  applied, and `/readyz` answers `503 {"status": "awaiting_config"}`. Binding early with an empty
  configuration would mean running with no `proxy.auth`, which is an open proxy.
- From then on, **readiness never depends on the control plane.** If the control plane is unreachable,
  that shows on `/v1/status` and `/metrics`, but not on `/readyz`. Otherwise a control-plane outage would
  take the whole fleet out of load balancers at once.

### Local HTTP API (replaces 0001's admin endpoints)

This is still one listener (`listen.*`, default `127.0.0.1:8080`), and it is still read-only. There are
no management endpoints on the instance. Management happens only over the outbound exchange.

| Method & path | Response | Change from 0001 |
|---|---|---|
| `GET /healthz` | `{"status": "ok"}` | unchanged |
| `GET /readyz` | `200 ready`; `503 starting \| awaiting_config \| stopping` | adds `awaiting_config` |
| `GET /v1/status` | Instance UID, version, mode, capabilities, config `{hash, status, error, applied_at}`, control plane `{connected, last_contact, last_error}`, health components, certificate expiry dates. No secrets, no hostnames. | new; replaces `/version` |
| `GET /metrics` | Prometheus text exposition (OpenMetrics when asked for in `Accept`) | new; replaces `/stats` |
| `GET /ca.pem`, `GET /ca.der` | The certificate clients must trust: the standalone root, or the fleet root in managed mode | unchanged paths |
| `GET /version`, `GET /stats` | removed | both were introduced in 0001 and never shipped, so no deprecation is needed |

`/v1/` is versioned from the start. Changes within v1 only add things. Removals are announced with the
`Deprecation` (RFC 9745) and `Sunset` (RFC 8594) response headers.

**Metrics.** Every label has a small, fixed set of possible values. **The intercepted host is never a
label.**

| Metric | Type | Labels |
|---|---|---|
| `mitm_proxy_build_info` | gauge (always 1) | `version` |
| `mitm_proxy_client_connections` | gauge | |
| `mitm_proxy_flows_total` | counter | `type` (`http`, `websocket`, `plain_http`) |
| `mitm_proxy_tunnels_total` | counter | `reason` (`out_of_scope`, `not_tls`, `sni_out_of_scope`) |
| `mitm_proxy_middleware_failures_total` | counter | `middleware` (registry names) |
| `mitm_proxy_oversize_passthrough_total` | counter | `direction` |
| `mitm_proxy_proxy_auth_failures_total` | counter | |
| `mitm_proxy_upstream_connections` | gauge | `protocol` |
| `mitm_proxy_config_applies_total` | counter | `result` (`applied`, `failed`) |
| `mitm_proxy_control_plane_last_contact_timestamp_seconds` | gauge | |
| `mitm_proxy_certificate_expiry_timestamp_seconds` | gauge | `kind` (`client`, `ca`) |

### Configuration (additions and changes)

| Key | Type | Default | Secret | Group | Meaning |
|---|---|---|---|---|---|
| `control_plane.url` | str | *(none)* | | bootstrap | The control plane's base URL (`https://` only). Empty = standalone. |
| `control_plane.enrollment_token` | str | *(none)* | **yes** | bootstrap | One-time enrollment token, via `_FILE`. Used only when there's no client certificate in `state_dir`. |
| `control_plane.ca_file` | str | *(none)* | | bootstrap | CA bundle for verifying the control plane. It replaces the system store for that connection. |
| `control_plane.wait_ms` | int | `50000` | | bootstrap | Longest long-poll the instance asks for. |
| `instance.labels` | list | *(none)* | | bootstrap | `key=value` pairs reported to the control plane. |
| `middleware.available` | list | *(none)* | | bootstrap | `name=module:attribute` registry. `log` is always available. |
| `middleware.chain` | list | *(none)* | | managed | **Changed:** names from the registry, in order. |

Validation adds these checks:

- the `control_plane.url` scheme is `https`;
- every label is `key=value`;
- registry names are unique and don't redefine `log`;
- in managed mode, no managed key is set locally.

### State directory (fixed layout)

```text
<state_dir>/
├── instance-id                    UUIDv7
├── identity/  client-key.pem (0600), client-chain.pem
├── ca/        standalone: ca.pem, ca-key.pem (0600)
│              managed: intermediate-key.pem (0600), chain.pem (intermediate + fleet root)
└── managed/   last-known-good.json (0600)
```

Managed mode **requires persistent `state_dir`.** Without it, every restart is a new instance needing a
new enrollment token. Kubernetes deployments become a StatefulSet with a PVC.

### CLI

- New: `mitm-proxy instance id` prints the UID, creating it if it doesn't exist yet.
- Changed: `mitm-proxy config` shows the mode, and marks each setting `bootstrap` or `managed`. In managed
  mode, it shows the last-known-good values for managed settings, with secrets masked.
- Enrollment happens automatically in `serve`. There is no separate command.

### Dependencies

- `httpx` (async HTTPS client with mTLS and timeouts) moves from dev to runtime. The stdlib has no async
  HTTP client. Reusing the proxy's own h11 upstream client was considered: it saves a dependency, but ties
  the management path to the data-plane internals that change most, and a bug in one would take out the
  other.
- `prometheus-client` (the reference implementation of the exposition format): see open question 2.

### Out of scope

- The control plane itself, its storage, its UI and its fleet operations.
- Commands from the control plane (drain, restart). The `ControlResponse` leaves room for a `commands`
  field, but v1 defines none.
- Software or package updates pushed by the control plane, and remote configuration of the instance's own
  telemetry. OpAMP has both.
- A WebSocket transport. The long-poll is enough, and WebSocket would be a later change of transport only.
- More than one control-plane URL, or failover between them. A single URL can sit behind DNS or a load
  balancer.
- Remote management of bootstrap settings.
- Serving the CA download from the proxy listener under a reserved "magic" hostname (the way mitmproxy
  does).

## Alternatives considered

- **The control plane pushes to a REST API on each instance.** Rejected. It needs an inbound,
  authenticated management port on every instance. That undoes the loopback default and fails behind
  NAT, firewalls and NetworkPolicies. The control plane would also have to track instance addresses.
- **OpAMP itself.** Deferred, not rejected. It is purpose-built for this job, but there's no maintained
  Python client we could confirm, the specification has still been moving, and it adds protobuf and
  WebSocket dependencies. Its concepts are copied here so that adopting it later is a change of transport.
- **gRPC or xDS-style streaming.** Rejected. `grpcio` is heavy and platform-specific, FastAPI can't serve
  it, the generated OpenAPI documentation stops working, it's hard to debug by hand, and xDS's semantics
  are notoriously hard to implement. It is far more than a lab tool needs.
- **A Kubernetes operator with custom resources (CRDs) as the control plane.** Rejected. It only works in
  Kubernetes, and the docker and systemd deployments would lose management.
- **Separate config-fetch and status-report endpoints.** Rejected. Two requests in flight can be
  reordered, and then the control plane can't tell which apply result belongs to which configuration.
  A single exchange with a sequence number avoids that (this is OpAMP's choice too).
- **Sending hashes of secrets in the effective configuration.** Rejected: low-entropy secrets can be
  brute-forced from them. `{"set": bool}` plus the config hash is enough.
- **Binding the proxy before the first configuration.** Rejected: until a configuration arrives, there
  would be no `proxy.auth`, so it would run as an open proxy.
- **Re-enrolling automatically after `401`/`403`.** Rejected. The token is single-use, so it would loop,
  and an instance that has been revoked should stay revoked until an operator acts.
- **Shipping middleware code, or module paths, in the configuration.** Rejected: that is remote code
  execution. The control plane chooses names from a local registry.
- **Letting `/readyz` depend on reaching the control plane.** Rejected. A control-plane outage would take
  the whole fleet out of service.
- **Local values overriding managed values (or the reverse).** Rejected. Two writers for one setting
  produce drift nobody can see. A key is either local or managed, never both.

## Consequences

**Easier:**
- Instances run anywhere they can make outbound HTTPS calls.
- Each configuration's outcome can be traced, through its hash and `APPLIED`/`FAILED` status.
- A control-plane outage changes nothing for traffic.
- Clients trust one fleet root.
- The OpAMP-shaped messages make a later move to OpAMP mechanical.

**Harder or costly:**
- We own the protocol semantics: sequence numbers, resuming after a disconnect, backoff, cancelling a
  held request. Those need tests against a fake control plane, run in-process with no network.
- Swapping configuration atomically needs every component to read from an immutable snapshot, not from
  `Config` fields read once at startup. That shapes the 0001 implementation from the start, which is why
  this record should be approved before 0001 is implemented.
- Kubernetes deployments need a StatefulSet and a PVC.
- Revoking an instance is easy. Re-enrolling one is a manual operator step.
- Every managed key exists twice: once as a local setting (standalone) and once in the managed schema.
  Both must come from the same validators, or they drift.

**Changes to 0001 before it is implemented:**
- the admin endpoints (above);
- `middleware.chain` becomes a list of names, plus `middleware.available`;
- the CA gets a managed (intermediate) source;
- settings are read from a swappable snapshot.

## Open questions

1. **Fleet CA.** Will the control plane be the CA and sign each instance's intermediate, as proposed? Or
   should managed instances keep their own self-generated roots, which is simpler but means clients
   install one root per instance? And should name constraints be required, or optional (as written)?
2. **Metrics dependency.** Add `prometheus-client`, or write the text exposition ourselves? The format is
   short for counters and gauges, but escaping, `# HELP`/`# TYPE`, and OpenMetrics negotiation are easy to
   get slightly wrong.
3. **`log_level`.** It is a bootstrap setting as proposed. Would you rather make it managed, so that the
   control plane can turn on DEBUG for one instance remotely?
4. **Commands.** Is it right to leave out drain and restart in v1? A control plane will want drain before
   decommissioning an instance. Adding commands later is additive, but needs its own capability.
5. **Before the first configuration.** Proposed: don't bind the proxy listener, so clients get "connection
   refused". The alternative is to bind and answer every request with `503`, which is friendlier to
   clients but a larger surface. Which do you prefer?
6. **The control plane's trust store.** `control_plane.ca_file` *replaces* the system store, which pins
   it to a private CA. `upstream.extra_ca_file` *adds* to it. Is that difference acceptable, or should
   both behave the same way?
7. **Config hash.** Proposed: the control plane computes the hash and the instance reports it back as an
   opaque value. Should the instance also recompute it from the canonical JSON and reject a mismatch,
   which would catch corruption at the cost of both sides needing identical canonicalization?
